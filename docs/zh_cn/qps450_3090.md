公平性与计量范围

两版均使用 V166、同一 RTX 3090、同一 5000 条数据、同一固定种子排列和相同生成参数。每个版本、每种并发在重启后恰好先处理 5000 次请求，再正式压测 3 分钟；四次预热均为 5000 成功、0 检查失败。正式结果没有 profiler，GPU 上没有第二个计算服务。完整耗时从 sse.open 之前计到流关闭，包含请求失败的耗时；成功必须满足 HTTP 200、DONE、非空内容、无解析错误。QPS 使用成功完成请求数和实际测试墙钟时间，包含末尾排空时间。未用首事件或默认 HTTP 指标替代完整 SSE 指标。

生成参数为 max_tokens=3、temperature=0、top_p=1、top_k=1、repetition_penalty=1，沿用数据中的聊天模板参数；模型输入未截短。两版平均输入约 7331~7334 token、平均输出约 2.40 token、平均缓存命中约 7304~7307 token。因而这是充分预热、重复请求、高前缀命中的短输出任务容量；不能外推为冷缓存、不同输入分布或长文本生成性能。两版缓存条件相同，未把更热的缓存当成优化收益。不同速度会完成不同数量的请求，虽然固定顺序和长度分布接近，仍非逐请求时间配对。

ByteLevel 改动从尾部16个 ID开始；不足8个非空 token 时向前扩展。它只缩短“输出反分词需要保存的前缀状态”，完整 prompt 仍进入模型。代码默认关闭，最终镜像通过 LMDEPLOY_QWEN2_BYTELEVEL_TAIL=1 开启。不缓存答案、不跳过推理、不改生成 token。CPU 微测与已有事件循环采样支持它是本轮关键改善点；最终 2.14 倍/2.07 倍结果属于 GPU、CPU 和预算设置组合，未进行逐项严格消融，不能把全部增益精确分配给单项改动。

SMs Active 描述 SM 存在活跃 warp 的周期比例；SM Issue 描述发射指令的周期比例，都不能直接解释为 FLOPS 利用率。平均 DRAM 活动也不能排除单个 kernel 的访存瓶颈。上述变化说明 kernel 并行度改善后，CPU 供给/调度间隙更明显，继续只追求 SM 百分比并不能保证请求更快。
